# 개발 기록 (프로토타입)

README에서 옮긴 세부 동작, 설정 근거, 시험 기록. 처음 쓰는 사람은 [README](../README.md)의 빠른 시작부터 보면 됨.
측정에 쓴 스크립트와 회의 녹음은 내부 평가 저장소(nineouting-ref, 비공개)에 있음.
평가 스크립트는 jjinsword 전용 평가 도구로, 그 환경(로컬 경로·모델 위치·녹음 파일)에서만 동작함. STT 서버 실행과는 상관없음.

## STT 개발 화면(8765)의 세부 동작

- 말하는 중의 글자가 타이핑되듯 나타나고, 발화가 끝나면 확정됨
- 스트리밍 STT가 놓친 말(화자가 틈 없이 바뀔 때의 대답 등)을 VAD로 찾아 다시 인식하고, 시각에 맞는 자리에 "보완" 표시와 함께 끼워 넣음
- 상단 "보완 N건" 버튼으로 보완된 줄만 모아 보고, 누르면 본문 위치로 이동
- 확정 줄마다 화자 번호 표시 ("화자 1" 등, 이름은 모름). 칩 옆 숫자는 판단 때의 유사도 (기준 0.60 이상이면 같은 화자, 밑줄=새 화자가 됨, 기울임=짧아서 가장 가까운 화자에 붙임). 칩에 마우스를 올리면 근거와 모든 화자와의 유사도가 나옴. 상단 "보기 설정" → "유사도"로 숫자 끄기
- 화자가 너무 많이 나뉠 때: 상단 "보기 설정" → "참석자 N명"을 넣으면 그 인원이 다 찬 뒤로는 새 화자를 만들지 않고 가장 가까운 화자에 붙임 (`--max-speakers N`으로 시작 시 지정 가능). 이미 생긴 화자는 줄이지 않음. 화자 칩을 누르면 다른 화자에 합칠 수 있음 (지난 줄 번호도 바뀌고 이후 판단에도 반영, 되돌릴 수 없음)
- 모델 확신도가 0.3 미만인 글자에 점선 표시 (상단 "보기 설정"에서 끄기). 회의 2 정답 기준 표시된 글자 중 약 27%가 실제 오류, 오류의 약 24%가 표시됨
- 보완 줄 전부와 확신도 낮은 글자가 있는 줄은 chunk-16·chunk-64 greedy로 다시 인식해, 결과가 다르면 "다른 결과" 버튼으로 보여줌 (진짜 2등 후보가 아님. sherpa-onnx 1.13.8에서 후보 목록을 꺼내는 방법은 찾지 못함)
- "다른 결과" 항목을 누르면 본문이 그 텍스트로 바뀜. 줄 끝 ✎로 직접 고칠 수 있음 (Enter 저장, Esc 취소). 고친 줄에는 "후보로 바꿈"/"직접 고침" 표시, 원래 결과는 선택지로 남아 되돌릴 수 있음. 고친 내용은 서버 기록과 자동 저장 파일에 반영됨
- 말이 아닌데 들어간 줄은 줄 끝 ✕로 지움 (저장 파일에는 `deleted`로 남고, 요약 쪽에는 삭제로 알림)
- STT가 아예 못 잡은 말은 줄 끝 ＋로 그 줄 다음에 직접 추가 (화자 선택 가능, "직접 추가" 표시). 시각은 앞 줄 끝과 다음 줄 시작의 가운데로 잡은 근사치
- 상단 "지우기"로 지금까지의 전사문을 지움 (서버 기록까지, 같은 주소를 연 다른 화면도 비워짐). 인식은 계속되고, 지운 시각보다 앞에서 시작한 줄은 나중에 도착해도 버림
- 맞장구·간투사로만 된 줄(네네, 그쵸, 어, 그 등)은 흐리게 하고 "맞장구"/"간투사" 표시. 상단 "보기 설정" → "맞장구 숨기기"로 숨김 (지우지 않음, 저장본에는 `kind`로 남음)
- 세션 (상단 버튼)
  - 서버를 켜면 세션이 시작되고 바로 전사함 (`--input ws`는 브라우저가 start를 보낼 때). 전사문은 줄이 바뀔 때마다 `transcripts/날짜_시각.jsonl`에 자동 저장 (비정상 종료에도 남음)
  - "● 녹음 시작": 같은 이름의 `.wav`로 녹음. 직전 최대 2분(세션 시작 이후분)도 함께 저장
  - "일시정지"/"계속": 전사와 녹음을 같이 멈춤. 멈출 때 무음 2.5초를 넣어 말하던 줄과 보완 판단을 마무리함
  - "완료": 세션 파일을 닫고 대기. 완료 뒤에 고친 내용도 그 세션 파일에 반영됨. "● 새 녹음 시작"을 누르면 화면을 비우고 새 파일로 시작
  - 파일 첫 줄 `_meta`의 `wav_t0`: 줄 시각(`start`) - `wav_t0` = wav 안의 시각. `gaps`(브라우저 입력): 멈춤 때 넣은 무음 [엔진 시각, 길이]
- 요약 쪽 상태창: 상단 "요약 전송" 버튼 → 받는 곳, 보낸 묶음 수, 성공·실패, 다음 전송까지 남은 초, 다음 묶음에 들어갈 줄·수정·삭제, 보낸 기록. 본문 줄마다 `대기`, `#3`, `수정 대기`, `#3 · 수정 #5`, `실패` 표시

## 설정 근거 (측정값)

- chunk-64, 후보 4 (SCRUM-23): 회의 2 정답 10분 CER chunk-16 7.4% → chunk-64 4.9%
- VAD 보완 (SCRUM-25): 회의 1 평가 구간 CER 26.5% → 20.8%, 삭제 162 → 76자 / 회의 2 4.9% → 5.1%, 삭제 53 → 32자 (실시간 동작, 기다림 2.0초)
- 줄 최대 10초 + 1초 다시 넣기 + 겹친 글자 거르기: 회의 2 9.0% → 5.6% (삽입 111 → 29자)
- blank penalty (최대 10초 + 1초·중복 거르기 기준)

  | blank penalty | 회의 1 CER · 대체·삭제·삽입 | 회의 2 CER · 대체·삭제·삽입 |
  |---|---|---|
  | 0 | 20.7% · 94·89·14 | 5.6% · 65·43·29 |
  | 0.25 | 19.6% · 107·60·19 | 5.5% · 66·34·34 |
  | **0.5 (기본)** | 19.8% · 111·47·30 | 5.7% · 74·23·41 |
  | 0.75 | 19.9% · 114·56·19 | 5.8% · 77·22·42 |
  | 1.0 | 20.9% · 93·57·49 | 6.5% · 79·24·56 |

  빠진 말은 화면에 안 보여 사용자가 고치기 어렵고 요약 쪽도 복원할 수 없음 → 전체 CER이 비슷한 0.25~0.5 중 삭제가 가장 적은 0.5. `reset_encoder`(21.5%·5.4%), VAD로 말소리 밖을 0으로 바꿔 넣기(20.8%·6.2%)는 채택하지 않음
- 핫워드 기본 31개 (`app/hotwords.txt`)
  - 구성: 회의 2 오인식에서 뽑은 21개(SCRUM-23) + 10-13 실제 회의 오류에서 뽑은 기술 용어 10개
  - blank penalty 0.5와 함께: 회의 1 19.8%(109·49·30), 회의 2 5.6%(70·25·41). 핫워드 없음은 19.8%·5.7%
  - 정답에 나온 용어 15번 중 맞힘 5 → 9번, 없는 곳에 끼워 넣기 0
  - 뺀 단어: 디비·레그(짧아서 다른 말을 끌어옴), 백엔드·전사문·정리본·요약본·회의록(흔한 말로 시작). 넣으면 회의 2 삭제 42 → 51자
  - 새 기술 용어 10개는 평가 녹음에 나오지 않아 효과 미측정
- `lowConfidence` (줄 글자 중 확신도 0.3 미만이 20% 이상): 2026-10-16 지금 설정으로 재측정 (회의 2 정답 구간 5개, 82줄 2,464자)
  - 걸린 줄 5개의 오류율(대체·삽입) 32.4%, 안 걸린 줄 4.1%. 전체 오류 중 걸린 줄에 있는 비율 10%
  - 10% 기준은 걸린 줄 오류율 19.8%(맞는 글자 80%를 요약에서 뺌), 30%는 50.0%·포착 8% → 20% 유지
  - 예전 설정(20초, 핫워드·blank penalty 없음)은 39.4%·포착 12%로 비슷함. 걸린 줄이 5~6개뿐이라 수치 흔들림이 큼
- 오프라인 모델(문장 전체 보기)로 다시 인식, VAD 보완 여유 늘리기, 보완 구간에 앞 문맥 붙이기: 모두 지금보다 나아지지 않아 채택하지 않음 (SCRUM-28)
- 화자 번호: TitaNet-small 임베딩을 발화마다 누적 비교. 유사도 0.60, 2초 미만 발화는 새 화자로 등록하지 않음. PoC 두 구간 DER 평균 8.2% (chunk-16 기준, chunk-64에서는 미검증). 발화자 구분은 제품에서 하지 않기로 함 (2026-10-16)

## 시험 기록

- wav(회의 1 평가 구간)를 실제 속도로 넣어 화면 동작 확인 (2026-10-13): 타이핑, 확정, 보완 줄 제자리 끼우기, 화자 번호, 보완 목록 패널, "최신으로" 버튼, 휴대폰 폭(375px)
- 세션 버튼을 wav 입력으로 확인 (2026-10-13): 녹음 시작(직전 18초 포함), 일시정지·계속, 완료, 새 세션, 완료 뒤 고치기가 각 파일에 저장됨
- 요약 쪽 전송을 시험용 받는 서버로 확인 (2026-10-14): 보낸 11개와 받은 11개가 같음, 보완 줄이 앞 시각으로 늦게 옴, 같은 주기 안에서 두 번 고치면 `rev` 2만 감, 보내기 전에 지운 줄은 묶음에서 빠짐
- 마이크 입력 문제 (2026-10-14, 맥 내장 마이크)
  - ffmpeg avfoundation으로 받으면 말할 때마다 틱 잡음. 같은 마이크를 음성 메모·sounddevice로 받으면 깨끗함 → 기본 입력을 sounddevice로 바꿈
  - ffmpeg 입력 서버 세션들에서 실제 시간 대비 엔진에 들어간 소리가 약 11% 짧았음. 같은 소리를 두 방식으로 동시에 받아 비교: ffmpeg 빠짐 11.3%·CER 12.1% / sounddevice 빠짐 0.0%·CER 11.8%. 실제 마이크 6분 30초에서도 빠짐 0.1% 이하. 서버 안에서 ffmpeg 경로만 빠지던 정확한 원인은 미확정
  - ffmpeg 입력(`--input ffmpeg`, 맥 전용)은 2026-10-16에 코드에서 지움 (윈도우 등 다른 환경 지원, 맥 전용 코드 정리). 필요하면 깃 기록에서 되살림
- 백엔드 전송 (2026-10-16, 70초): 요청 간격 최소 0.5초, 연결 1개로 49번 요청, rev 역전·확정 뒤 재전송 0번, 보완 줄이 앞 시각으로 도착, 받는 서버가 6초 동안 503을 낸 사이의 줄을 모두 다시 받음
- 브라우저 입력 (2026-10-16, 회의 1 wav 42초를 파이썬 클라이언트로): 12초에 끊고 5초 뒤 다시 연결해 몰아 보냄, 25초에 3초 멈춤, 두 번째 연결 거절(1008), end 뒤 세션 완료. 줄 시각이 wav 직접 입력과 같음(26.9 → 26.94초). 몰아 보내는 동안 말하는 중 줄은 백엔드로 0번. 브라우저 마이크로 `/sender` 자막·지연 측정 확인
- 음성 연결 입장권 (2026-10-20, 가짜 백엔드로): 올바른 입장권만 받아들이고 재사용·없는 입장권·입장권 없이·경로 없이는 모두 `1008`로 거절. 백엔드를 끈 채 연결해도 거절(3초 기다린 뒤). 연결 주소·`start`·확인 응답의 `meetingId` 중 하나만 달라도 거절
  - 고치다 찾은 것: 연결을 등록한 뒤 `remote_address`를 읽다 상대가 벌써 끊었으면 `OSError`가 나는데, 그 줄이 `try` 밖이라 `finally`가 돌지 않아 죽은 연결이 등록된 채 남았음
- 회의 알림 (2026-10-20, wav로 start → 6초 → 멈춤 2초 → 재개 → 6초 → 끝): 알림 4개가 순서대로 나감. `atMs`는 start 0, pause 6,000, resume 6,000(멈춘 동안 늘지 않음), end 12,000(마무리용 무음 2.5초가 빠짐). `end`가 마지막 확정 줄(endMs 13,140) 뒤에 도착
  - 장애 중 몰아 보내기: 가짜 백엔드를 10초 동안 503으로 두자 `pause`가 2초 간격으로 다시 시도되고, **그동안 `resume`은 보내지 않음**. 복구 뒤 `pause` → `resume` 순서로 나감. 같은 구간에 전사 줄은 0.5초마다 재시도되어 복구 뒤 모두 전달됨
- 재연결 대체 (2026-10-20, wav 16초를 파이썬 클라이언트로): 첫 연결을 닫지 않은 채 두 번째 연결을 열어, 서버가 끊김을 아직 모르는 상황을 만듦. 두 번째 연결이 받아들여지고 첫 연결은 `4001 replaced by a new connection`으로 닫힘. 이어받은 연결의 `ready`가 `meetingMs: 8000`을 돌려주고, 백엔드로 간 줄 시각이 0 → 5,820 → 11,100ms로 이어짐. end 뒤 세션 완료
  - 2026-10-16에 "두 번째 연결 거절(1008)"로 확인했던 동작을 바꾼 것임 (CN팀 S6)
- 회의 도중 STT 재시작 (2026-10-29, SCRUM-119): 회의 녹음 60초 지점부터 20초를 파이썬 클라이언트로 실제 속도로 보낸 뒤 STT를 SIGKILL로 끄고, 새 STT에 `offsetMs: 20000`으로 다음 20초를 이어 보내고 end. 가짜 백엔드 결과 (측정값)

  | | 재시작 전 줄 | 재시작 뒤 줄 | 확정 뒤 같은 seq (규칙 위반) |
  |---|---|---|---|
  | 고치기 전 (seq = 엔진 줄 번호) | 3 (seq 1~3) | 0 (모두 버려짐) | 12 |
  | 고친 뒤 (seq = `offsetMs // 10` + 세션 안 번호) | 3 (seq 1~3) | 3 (seq 2001~2003) | 0 |

  - 고치기 전에는 새 STT가 seq 1부터 다시 세어, 이미 확정된 seq 1~3에 막힘. meeting-service도 같은 규칙(`rev`가 크고 확정 전일 때만 덮어씀)이라 204로 답하고 버림 → STT는 보낸 줄로 여김
  - 재시작 전 부분의 seq·글자·시각은 두 경우가 같음
- 밀린 줄 500줄 넘김 (2026-10-29, SCRUM-120): 가짜 백엔드(meeting-service처럼 한 요청 500줄 넘으면 400)를 10초 동안 503으로 두고, 그동안 확정 줄 1,234개를 `BackendSender`에 넣은 뒤 복구. 줄은 가짜지만 HTTP는 가짜 백엔드를 거침 (측정값)

  | | 도착한 줄 | 복구 뒤 요청 | 400 | 요청 최대 줄 수 |
  |---|---|---|---|---|
  | 고치기 전 (한 요청에 다 담음) | 0 / 1,234 | 1,234줄 요청이 계속 거절됨 | 41번 | 1,234 |
  | 고친 뒤 (500줄씩 나눔) | 1,234 / 1,234 | 500 · 500 · 234 세 번에 끝남 | 0번 | 500 |

  - 고치기 전에는 실패한 줄이 다음 주기에 같은 묶음으로 다시 나가 계속 500줄을 넘음 → 복구된 뒤에도 그 회의 줄이 하나도 저장되지 않음. end는 3초 기다린 뒤 줄이 남은 채로 나감
  - 고친 뒤 실패 중(10초)에는 0.5초마다 500줄 요청 1번만 나감 (19번). 한 묶음이 실패하면 그 주기를 멈추므로 요청 수가 늘지 않음
  - end는 마지막 묶음 뒤에 도착
  - 평소 전송: 회의 녹음 60초를 `--wav`(실제 속도)로 넣고 고치기 전후를 비교. 요청 37번 · 요청당 최대 1줄 · 최소 간격 0.5초 · 확정 줄 10개(seq·시각·글자)가 모두 같음
